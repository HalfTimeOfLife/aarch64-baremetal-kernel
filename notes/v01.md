## Step 0: QEMU `virt`

### What is QEMU `virt`?

QEMU is a machine emulator. It allows us to run our AArch64 kernel without physical ARM hardware.

The `virt` machine provides a virtual CPU, RAM and peripherals such as a PL011-compatible UART.

### Memory Layout

The simplified memory layout relevant to this project is:

```text
 _______________ 0x00000000
|     Flash     |
|_______________|
|               |
|               |
|               |
|               |
|               |
|_______________|0x40000000
|      RAM      |
|_______________|
```

## Step 1: What is AArch64 ?

### Registers

| Register      | Name / Meaning | Main purpose |
| ------------- | -------------- |------------- |
| `X0-X30`      | General-Purpose Registers (GPRs) | General integer data, addresses, function arguments and return values |
| `W0-W30`      | 32-bit views of `X0–X30` | Access the lower 32 bits of the corresponding `X` register |
| `XZR` / `WZR` | Zero Register| Always reads as zero; writes are discarded |
| `SP`          | Stack Pointer                         | Points to the current stack frame / top of the stack                        |
| `PC`          | Program Counter                       | Address of the current instruction; not directly accessible as a normal GPR |
| `X30`         | Link Register (`LR`)  - ARCHITECTURAL | Holds the return address for subroutine calls (`BL`, `BLR`)                 |
| `X29`         | Frame Pointer (`FP`) - CONVENTIONAL | Commonly used to point to the current stack frame                           |
| `CurrentEL` | Current Exception Level | System register containing the current exception level |

### Instructions

| Instruction | Main purpose | Operation | Example |
| --- | --- | --- | --- |
| `MOV` | Copy a value between registers. | `x0 = x1` | `mov x0, x1` |
| `ADR` | Load the address of a nearby label. | `x0 = address(_start)` | `adr x0, _start` |
| `LDR` | Load data from memory. | `x0 = memory[x1]` | `ldr x0, [x1]` |
| `STR` | Store a 64-bit value to memory. | `memory[x1] = x0` | `str x0, [x1]` |
| `LDRB` | Load one byte from memory. | `w0 = memory[x1]` | `ldrb w0, [x1]` |
| `STRB` | Store one byte to memory, useful for UART. | `memory[x1] = low_byte(w0)` | `strb w0, [x1]` |
| `ADD` / `SUB` | Add or subtract values. | `x0 = x0 + 1` | `add x0, x0, #1` |
| `CMP` | Compare two values. | Set flags for `w0 - 0` | `cmp w0, #0` |
| `AND` / `ORR` | Clear or set selected bits. | `w0 = w0 & 0xff` | `and w0, w0, #0xff` |
| `B` | Unconditional branch. | `PC = address(loop)` | `b loop` |
| `BL` | Call a function; saves the return address in `X30`. | `X30 = next instruction`, then branch | `bl uart_putc` |
| `RET` | Return from a function. | `PC = X30` | `ret` |
| `B.EQ` / `B.NE` | Branch after a comparison. | Branch if equal / not equal | `b.ne loop` |
| `CBZ` / `CBNZ` | Branch if a register is zero or non-zero. | Branch if `w0 == 0` / `w0 != 0` | `cbz w0, done` |
| `MRS` / `MSR` | Read or write a system register. | `x0 = CurrentEL` | `mrs x0, currentel` |

The usual order is **destination first, then source**. Therefore, `mov x0, x1` means “copy the value in `x1` into `x0`”; it does not copy `x0` into `x1`.

### Exception levels (`EL0` - `EL3`)

Exception levels define the privilege level of the code currently running.
Higher levels have more control over the processor and system resources.

| Exception level | Typical use | Privilege |
| --- | --- | --- |
| `EL0` | User applications | Lowest |
| `EL1` | Operating system kernel | High |
| `EL2` | Hypervisor or virtual machine monitor | Higher |
| `EL3` | Secure monitor and firmware | Highest |

For a minimal bare-metal kernel, the kernel normally runs at `EL1`. During early boot, check `CurrentEL` to find the level where the processor started.

## Step 2: The boot

```asm
.section .text.boot

.global _start
_start:
    // Setup stack
    ldr x0, =_stack_top
    mov sp, x0

    b .
```

### Setup the stack

```
ldr x0, =_stack_top
mov sp, x0
```

1. **Why `ldr x0, =_stack_top` and not `mov sp, _stack_top` ?**

`_stack_top` represents an address which might be too big for encoding in certains mov form. With `ldr ..., =...`, the assembler can load the symbol's full address 

2. **Why use `x0` and not directly pass it to `sp` ?**

`sp` can't be used as a destination's register by this form of `ldr`.

3. **What is `_stack_top` ?**

`_stack_top` will be a symbol defined by the linker which represents the top of the memory zone reserved for the stack.

4. **What is `b .` ?**

The `.` represents the current instruction/address. The processor executes the same instruction infinitely, i.e, `b .` is an infinite loop.

## Step 4: UART

> See [PrimeCell UART (PL011) Technical Reference Manual](https://support.arm.com/documentation/ddi0183/g/?lang=en)

### What is UART?

UART (Universal Asynchronous Receiver-Transmitter) is a hardware peripheral used for serial communication.

We will communicate directly with the UART hardware through memory-mapped I/O (MMIO).

### QEMU `virt` UART

QEMU's `virt` machine exposes a PL011-compatible UART.

The UART is mapped at:

    UART_BASE = 0x09000000

> See [qemu/hw/arm/virt.c](https://github.com/qemu/qemu/blob/master/hw/arm/virt.c)

The important registers for our minimal driver are:

| Register | Offset | Purpose |
| --- | --- | --- |
| `UART_DR` | `0x00` | Data register |
| `UART_FR` | `0x18` | Flag register |
| `UART_TXFF` | `0x20` | Transmit FIFO full flag |

Therefore:

    UART_DR = UART_BASE + 0x00
    UART_FR = UART_BASE + 0x18

> See [PrimeCell UART (PL011) Technical Reference Manual](https://support.arm.com/documentation/ddi0183/g/?lang=en) at *Summary of registers*, page 3-3

### Memory-mapped I/O

The UART registers are accessed like memory.

For example:
```asm
ldr x1, =UART_BASE
ldr w2, [x1, #UART_FR]
```

These instructions do not access normal RAM.

The address `0x09000000` is handled by the QEMU `virt` machine as the
UART peripheral.

The CPU therefore communicates with the UART using normal load and
store instructions at specific memory addresses.

### `UART_FR`

`UART_FR` is the UART Flag Register.

For transmission, we are interested in the `TXFF` bit.

`TXFF` means "Transmit FIFO Full".

The mask is:
```asm
.equ UART_TXFF, 0x20
```
    

Bit 5 is tested with:
```asm
tst w2, #UART_TXFF
```
    

If the bit is set, the transmit FIFO is full and we must wait.
```asm
wait:
    ldr w2, [x1, #UART_FR]
    tst w2, #UART_TXFF
    b.ne wait
```

The CPU repeatedly reads the UART status register until the UART is ready to accept another character.

> See [PrimeCell UART (PL011) Technical Reference Manual](https://support.arm.com/documentation/ddi0183/g/?lang=en) at *Flag Register, UARTFR*, page 3-8

### `uart_putc`

Our first UART function writes a single character.

```asm
.global uart_putc

.equ UART_BASE, 0x09000000
.equ UART_FR,   0x18
.equ UART_DR,   0x00
.equ UART_TXFF, 0x20


uart_putc:
    ldr x1, =UART_BASE

wait:
    ldr w2, [x1, #UART_FR]
    tst w2, #UART_TXFF
    b.ne wait

    str w0, [x1, #UART_DR]

    ret
```

The character is passed in `w0`.

The function:

1. Loads the UART base address.
2. Reads `UART_FR`.
3. Tests the `TXFF` bit.
4. Waits while the FIFO is full.
5. Writes the character to `UART_DR`.
6. Returns with `ret`.

### `uart_puts`

Writing one character is useful, but printing a complete string requires repeatedly calling `uart_putc`.

Our string function receives a pointer to a null-terminated string in `x0`.

```asm
uart_puts:
    stp x19, x30, [sp, #-16]!
    mov x19, x0

loop:
    ldrb w0, [x19], #1
    cbz w0, done
    bl uart_putc
    b loop

done:
    ldp x19, x30, [sp], #16
    ret
```

### Reading the string

`ldrb` loads one byte from memory:
```asm
ldrb w0, [x19], #1
```

The current character is loaded into `w0`, and `x19` is then
incremented by one byte.

For:
```text
"HELLO"
```
the function reads:
```text
'H'
'E'
'L'
'L'
'O'
'\0'
```

### Detecting the end of the string

Strings are terminated by a null byte:
```text
'\0' = 0x00
```
We detect it with:
```asm
cbz w0, done
```
If `w0` is zero, the string is finished.

Otherwise the character is printed:
```asm
bl uart_putc
b loop
```
### Why save `x19`?

`x19` is used to keep the string pointer while `uart_puts` calls another function.

`x19` is a callee-saved register according to the AArch64 calling convention.

Therefore it is saved before use:
```asm
stp x19, x20, [sp, #-16]!
```

and restored before returning:
```asm
ldp x19, x20, [sp], #16
```
The stack remains 16-byte aligned.

### Calling `uart_puts` from `_start`

The boot code can now load the address of a string into `x0` and call `uart_puts`.
```asm
.section .text.boot

.global _start
.extern uart_puts

_start:
    ldr x0, =_stack_top
    mov sp, x0

    ldr x0, =message
    bl uart_puts

hang:
    b hang

.section .rodata

message:
    .asciz "Hello, AArch64!\n"
```

The execution flow is:
```text
    _start
        |
        +-- setup stack
        |
        +-- load message address into x0
        |
        +-- call uart_puts----------------+
                |                         |
                +-- read one character    | 
                |                         |
                +-- call uart_putc        |
                |                         |
        +-------+-- repeat ---------------+
        |
        +-- infinite loop (`b .`)
```

## Step 5: Compilation

The project uses the `aarch64-none-elf` cross toolchain.

The source files are first assembled into object files.
```text
    boot.s
       |
       v
    boot.o

    uart.s
       |
       v
    uart.o
```
The linker then combines the object files according to `linker.ld`.
```text
    boot.o + uart.o
          |
          v
    aarch64-none-elf-ld
          |
          v
      kernel.elf
```

The resulting ELF file contains the executable kernel and the addresses assigned by the linker.

### Makefile

The Makefile automates this process.

The important commands are:
```bash
    aarch64-none-elf-gcc -c source.s -o object.o
```

and:
```bash
    aarch64-none-elf-ld -T linker.ld -o kernel.elf objects.o
```

`gcc` is used here as the assembler driver, while `ld` performs the final linking step.

The kernel is linked using our custom linker script instead of the default linker configuration.

## Step 6: Verify the kernel

After compilation:
```bash
    make clean
    make
```

The generated ELF can be inspected with `nm`:

    aarch64-none-elf-nm build/kernel.elf

This allows us to verify symbols such as:
```text
    _start
    uart_putc
    uart_puts
    _stack_bottom
    _stack_top
```
The generated machine code can be inspected with:
```text
aarch64-none-elf-objdump -d build/kernel.elf
```

This is useful for checking that the assembler has generated the expected AArch64 instructions.

For example:

    ldr x0, =_stack_top

is an assembler pseudo-instruction. The disassembly allows us to see how it was actually encoded in the resulting ELF.

## Step 7: Run the kernel

The kernel can be executed with:
```bash
    qemu-system-aarch64 \
        -M virt \
        -cpu cortex-a57 \
        -nographic \
        -kernel build/kernel.elf
```

Expected output:
```text
Hello, AArch64!
```

At this point the kernel:

1. Starts executing at `_start`.
2. Initializes the stack.
3. Loads the address of the string.
4. Calls `uart_puts`.
5. Reads the string one byte at a time.
6. Polls the UART transmit FIFO.
7. Writes each character to the UART.
8. Returns to the instruction following `bl uart_puts`.
9. Enters the infinite loop.

This completes v0.1.
